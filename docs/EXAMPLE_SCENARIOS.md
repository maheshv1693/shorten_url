# AI-Assisted Engineering Scenarios

These examples show how an engineer can use AI to structure implementation work while retaining responsibility for scope, design decisions, code review, and validation. The application does not accept engineering requirements or autonomously generate software; these are documented development workflows around the URL shortener prototype.

## 1. Greenfield: URL Shortener

### Requirement

> Build a scalable URL shortener service with APIs, persistence, and analytics.

### Clarifications and assumptions

- The initial deliverable is a locally runnable prototype; no traffic volume, latency SLO, availability target, or deployment topology was specified.
- The first API supports URL creation, redirects, and click analytics. Custom aliases and optional expiration are included.
- SQLite and a process-local cache are acceptable for local evaluation. PostgreSQL, Redis, and durable telemetry are production roadmap items.
- Generated codes use secure random seven-character Base62 strings. A database uniqueness constraint is authoritative, with at most three insertion attempts.
- Click totals currently count recorded redirect requests; bot filtering and unique-visitor semantics are not implemented.

### Engineer-led task breakdown

1. Identify code-generation, concurrency, expiry, analytics-loss, abuse, and privacy risks before choosing implementation details.
2. Define SQLAlchemy models, Pydantic request/response contracts, and database session lifecycle.
3. Implement code generation, persistence, collision handling, and repository operations.
4. Add a cache-aside redirect path with expiry-aware TTLs.
5. Add URL creation, redirect, analytics, and health endpoints.
6. Add focused unit and HTTP integration tests, then document setup and limitations.

### AI assistance and engineer decisions

- AI helped produce the initial risk checklist, model/schema draft, Base62 utilities, repository operations, cache, endpoints, and test cases.
- I chose SQLite and in-memory caching for a reproducible local prototype, while recording PostgreSQL, Redis, and durable queues as production work.
- An initial sequential-ID/Base62 choice was later rejected after reviewing enumeration risk. The current implementation uses `secrets.choice`; database uniqueness and bounded retries handle random collisions.
- An integration-test failure exposed that manually advancing the database dependency bypassed test overrides. The redirect route was changed to use FastAPI `Depends`.

### Outputs and validation

- Implementation: `app/core/`, `app/db/`, `app/api/v1/`, and `app/main.py`.
- Tests: `tests/test_base62.py`, `tests/test_cache.py`, `tests/test_repository.py`, and `tests/test_api.py`.
- Validation: `python -m pytest -v` passed 43 tests after the API authentication update. Live checks also exercised health, creation, 307 redirects, and analytics.

### Trade-offs and limitations

“Scalable” is not a measured claim: no load test or production SLO has been established. SQLite, a per-process cache, and FastAPI in-process background tasks are prototype choices. Seven-character codes reduce sequential enumeration but are not authorization; rate limiting and a longer code policy should be evaluated for production.

## 2. Brownfield: Improve an Existing Shortener

### Requirement

> The existing service rejects an empty alias from a form and generates sequential short codes. Make blank aliases use generated codes, reduce code predictability, and preserve duplicate-alias behavior.

### Clarifications and assumptions

- A missing, empty, or whitespace-only alias means “generate a code.”
- A nonblank alias remains subject to the existing 4–16 character and allowed-character validation.
- A duplicate custom alias returns `409 Conflict`; autogenerated collisions are retried up to three times before failing.
- Random short codes reduce predictability but do not provide access control.

### Engineer-led task breakdown

1. Reproduce the empty-alias validation error and inspect the existing code-generation path.
2. Normalize blank aliases before field constraints are applied.
3. Replace sequential generation with a cryptographically secure seven-character Base62 generator.
4. Keep the database unique constraint as the concurrency-safe collision arbiter and add bounded retries.
5. Add regression tests for blank aliases, custom alias conflicts, generated-code format, retry success, and retry exhaustion.
6. Update architecture and risk documentation to remove obsolete guarantees.

### AI assistance and engineer decisions

- AI helped trace the validation and persistence paths, suggest `secrets.choice`, and draft focused regression tests.
- The engineer retained database-enforced uniqueness rather than relying on a race-prone pre-insert availability check.
- The engineer kept the retry limit bounded and documented that random generation is probabilistic; it does not eliminate collisions.

### Outputs and validation

- Changes: `app/api/v1/schemas.py` normalizes blank aliases; `app/db/repository.py` generates random codes and retries; architecture and README descriptions were updated.
- Regression coverage: `test_blank_custom_alias_generates_code`, `test_create_url_generates_seven_character_base62_code`, `test_create_url_retries_generated_code_collision`, and `test_create_url_stops_after_three_generated_code_collisions`.
- Validation: repository tests cover code generation and retry behavior; API tests cover blank aliases, redirects, health, and analytics. The full suite passed 40 tests after this brownfield change.

### Trade-offs and limitations

Random codes can collide, so the database constraint and retry behavior are essential. Seven Base62 characters provide about 41.7 bits of keyspace and should not be described as “high-entropy” or as preventing harvesting. Production should consider authentication, longer codes, rate limiting, monitoring, and a durable analytics pipeline.

## 3. Ambiguous Requirement: News Agency and WhatsApp

### Requirement

> “We send news links to readers over WhatsApp and want branded short links and click analytics.”

### Clarifying questions and assumptions

- Does “branded” mean readable aliases, a custom short-link domain, or both?
- Which WhatsApp channel or provider sends messages, and is message delivery part of this project?
- Should analytics count every request, filter previews and bots, or report unique readers? What retention and privacy rules apply to IP address and user-agent data?
- Should links expire, and what are the expected traffic, latency, and availability targets?

For this prototype, assume the service creates short links and records redirect click events. It does **not** send WhatsApp messages, integrate with the WhatsApp Business API, configure a custom branded domain, filter bots, or provide production-scale analytics guarantees. The short URL currently uses the incoming request host.

### Engineer-led task breakdown

1. Separate URL shortening and click analytics from the external message-delivery workflow.
2. Use the existing `POST /api/v1/urls` contract to create each article link; leave the alias blank for an automatically generated code or supply a valid alias.
3. Include the returned short URL in the agency’s existing WhatsApp workflow; message sending remains out of scope.
4. Let reader requests reach `GET /{short_code}`, redirect with HTTP 307, and record click metadata asynchronously.
5. Query `GET /api/v1/urls/{short_code}/analytics` to inspect event totals and recent events.
6. Before launch, decide on domain verification, preview/bot filtering, analytics retention, rate limits, and traffic targets.

### AI assistance and engineer decisions

- AI helped turn the broad product statement into clarifying questions, scope assumptions, API tasks, and a validation checklist.
- The engineer scoped out WhatsApp delivery and branded-domain provisioning rather than implying those capabilities exist in the prototype.
- The engineer treats raw click counts as request counts, not verified human readers or unique audience reach.

### Example API flow

Create a link without choosing an alias:

```bash
curl -X POST "http://127.0.0.1:8000/api/v1/urls" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://news.example.com/story/markets-today",
    "custom_alias": "",
    "expires_in_hours": 24
  }'
```

Representative response (the generated code will differ):

```json
{
  "short_code": "R7xKm2A",
  "short_url": "http://127.0.0.1:8000/R7xKm2A",
  "original_url": "https://news.example.com/story/markets-today",
  "created_at": "2026-09-28T12:00:00Z",
  "expires_at": "2026-09-29T12:00:00Z"
}
```

Use the returned link in the agency's message, then validate redirect and analytics behavior:

```bash
curl -i "http://127.0.0.1:8000/R7xKm2A"
curl "http://127.0.0.1:8000/api/v1/urls/R7xKm2A/analytics"
```

### Outputs and validation

- API contract and implementation: `app/api/v1/schemas.py`, `app/api/v1/endpoints.py`, and `app/main.py`.
- Existing integration coverage: `tests/test_api.py::test_create_url_returns_absolute_short_url`, `tests/test_api.py::test_redirect_returns_temporary_redirect`, and `tests/test_api.py::test_analytics_includes_redirect_click`.
- Validation: automated tests verify URL creation, 307 redirect behavior, and click analytics. They do not validate WhatsApp delivery, branded-domain DNS/TLS, or human-versus-bot attribution.

### Trade-offs and limitations

The existing analytics endpoint reports click events and recent metadata; it does not prove that a person read a story. Browser link previews and automated scanners may contribute events. Custom aliases are user-chosen and guessable. Production use needs product decisions on branded domains, bot filtering, privacy/retention, abuse controls, and durable event processing.
